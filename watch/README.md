# gaga ai 手表客户端

嘎嘎的"第二副身躯"：手表形态的**设备侧客户端**（ADR-051）。协议直连 `gaga/up`/`gaga/down`，服务端零改动——手表就是"又一个嘎嘎设备"，与 `esp32-idf/` 是同一层。

**定位**：手机是最短 AI 路径（飞书+输入法都在），不需要"手机嘎嘎"；穿戴才是空地——厂商手表的 AI 锁死在自家生态，进不了你的飞书群。手表 APK 与胸前硬件共享同一颗服务端大脑、同一套帧协议、同一个飞书群。

> **为什么是独立工程而不是 `app/` 的子模块**：`app/` 的宪法是"永远是哑管道"，手表是设备侧客户端（自己组帧、走信令状态机），塞进 `app/` 会让那条铁律自相矛盾。所以 `watch/` 与 `app/`、`server/`、`esp32-idf/` 平级，各自独立构建，互不依赖。

## 目标硬件

**OPPO Watch X3**（内部型号 `OWW231`，ColorOS Watch / Android 11 API 30，圆屏 **466×466 px @320dpi**）。

> ⚠️ **布局尺寸先量再画**：466px @320dpi = **233×233 dp**（不是 466dp）。
> v0.2.0 就是按像素拍脑袋画的布局，结果面板 318dp 溢出圆屏、按钮被挤到可视
> 区外点不动（ADR-052 修订①）。横向内边距至少 32~36dp 防圆角裁字，字号按
> 233dp 算（按钮 13sp / 正文 11sp / 辅助 9sp），所有长页面用 ScrollView 兜底。

Opus 编码用 Android 系统 `MediaCodec`（API 29+ 运行时探测），Android 11 满足。

## 装机（ADB）

```bash
adb install -r build/outputs/apk/debug/gaga-watch-debug.apk
```

OPPO Watch 的 USB 授权有几个坑，踩过的都在这：

1. **USB 用途要改成"传输文件/MTP"**——默认"仅充电"时 ADB 接口根本不枚举，表现是 `adb devices` 空、Mac 的 USB 树也看不到设备（只有充电电流）。此时手表上**不会**弹"允许 USB 调试"，因为接口压根没起来。
2. **开发者选项里两个独立开关都要开**：`USB 调试` ✅ + `仅充电模式下允许 ADB 调试` ✅（OPPO 特有，后者关掉时插上只会充电）。
3. 授权框会被息屏/表盘盖住——插上时保持亮屏，或下拉通知找。
4. 无线调试（Android 11 有）是备用通道：设置 → 开发者选项 → 无线调试 → `adb pair`。

## 网络路径（不限于 WiFi）

手表要的是 **IP 可达 broker**，链路任意：

| 链路 | 手表侧地址 | 到 broker 的路径 | 可行性 |
|---|---|---|---|
| WiFi 直连 | 与 broker 同网段 | 直连 | ✅ 最稳 |
| **蓝牙 PAN（手机「蓝牙网络共享」）** | `192.168.44.x` 之类独立网段 | 手机路由转发 | ✅ 可行 |
| 手机热点 | 手机分配的网段 | 手机路由转发 | ✅ 可行 |

蓝牙 PAN 要成立的三件事：

1. **手机端「蓝牙网络共享」开关打开** —— 设置 → 连接与共享。⚠️ 这跟"蓝牙已配对"是两件事，配对不等于网络共享。
2. **手表真连上 PAN 并拿到 IP** —— 手表设置 → 蓝牙里看网络状态。
3. **手机 ROM 的蓝牙 NAT 不拦内网** —— 部分厂商只放行外网不放行局域网，只能实测。

带宽方面：蓝牙 PAN 实际 1~3Mbps，Opus 上行 24kbps 跑得动，但延迟比 WiFi 差。

### 自查工具（设置页「网络诊断」区，不用 adb）

- **本机 IP 列表**：枚举所有非回环网卡的 IPv4。蓝牙 PAN 会以 `bnep`/`bt-pan` 之类接口出现——**看得到地址 = 手机把网分过来了**；看不到 = 共享没开。
- **测试连接 broker**：不走 MQTT，直接 TCP 连 `host:port`（4s 超时），结果就地显示。
  - **TCP 通** → 网络可达，MQTT 还连不上就查 broker/端口/防火墙
  - **TCP 超时** → 链路问题，查蓝牙共享开关 / 手表有没有拿到 IP

## 交互（ADR-052 → ADR-057）

| 场景 | 效果 |
|---|---|
| **启动**（系统快捷方式：表盘紧握松开 / 双击右下键） | **录音先行渲染后行**：onCreate 先开录（进程 ~200ms，早于 UI/MQTT——帧进离线缓冲连上补发不丢；开录"嘎"一声）再 inflation。**录音中无卡片**（红色状态丸），点击发送才建卡。首屏只渲染最新 2 张卡，旧卡点"更早的 N 条"展开。打开即自动录音（设置里可关）。紧握只在**表盘态**有效（ADR-060 实测） |
| **结束录音：上下甩两下 / 左右摆两下手腕**（ADR-060 判据 v2） | **同轴反向交替双脉冲**才触发：第一下甩出去、第二下甩回来，1.4s 内完成。走路/骑车颠簸是同向冲击，天然不误触；平摆不翻掌，不触发转腕灭屏 |
| App 在前台时再次被系统唤起（如双击右下键快捷方式） | `onNewIntent` → 切换录音（ADR-058 路径，仅对系统级唤起有效） |
| **灭屏 / 切后台时正在录音** | 自动收尾发送（ADR-060 兜底：灭屏后手势没了、网可能被掐，挂着只会烂在缓冲里）；App 运行期间屏幕保持常亮 |
| **点消息卡** | 进详情页看全文（列表里 ask 截 60 字 / reply 截 80 字） |
| **从左往右滑** | 返回上一层（v0.3.2）：任何非首页视图（嘎嘎页/面板/设置/调试/详情）右滑都回首页 |
| 状态胶囊 / 嘎嘎页鸭子 / 录音按钮 | 点 = 录音/停止 |
| 首页左滑 | 嘎嘎页 |
| 顶部下滑 | 快捷面板（提示音开关 + 设置 + 调试） |

**物理键零接触（ADR-059）**：App 不消费、不拦截、不映射任何物理键（含媒体键）——系统键留给系统。调试页的按键记录是纯观察。

**状态四态**（鸭子跟着变色，不看字也能一眼看出）：待机（鸭黄）→ 录音中（红）→ 发送中（橙）→ 接收中（绿）。

**为什么是"切换"而不是"按住说话"**：胸前两段式按钮有"稍微松力就断"的物理手感问题（2026-09-25 真机反馈），手表屏小手滑，切换式最稳——ADR-045 v1 废弃时踩过的同款坑。

**为什么是"反向交替的两下"而不是"一下"或"同向两下"（ADR-060 判据 v2）**：一下冲击的误触源太多（走路摆臂、骑车颠簸、抬手看表）；v1 的合矢量判据连"同向两下"也认，而步频两步间隔 ~600ms 恰好落在配对窗里。v2 要求**同轴、方向相反**（甩出去、甩回来）——刻意动作才有这个特征，颠簸类天然免疫。判定参数：单晃余震去抖 350ms、配对窗 1400ms、触发冷却 1500ms；调试页实时指引（"待第1晃 / 等X+反向 x.xs"）。

## 鸭子声音语言（与 `esp32-idf/main/audio/` 同源）

| 事件 | 声音 | 实现 |
|---|---|---|
| 开始录音 | **嘎**（1 声） | 真鸭叫采样 `snd_quack.wav`（16kHz/305ms），SoundPool |
| 发送完 | **嘎嘎**（2 声，对齐 ESP32 `SndEv::Sent`） | 同款采样连放两次（2026-09-30 拍板：开始/结束都有嘎，声数区分） |
| 收到回复 | **叮咚**（= 钉钉音） | 1318Hz 120ms → 988Hz 180ms，线性衰减包络 |
| 出错 | **噗噗** | 70~130Hz 锯齿随机游走 + 噗呲断续包络 |

无独立开机提示音（2026-09-30 用户拍板）：唤起即录的那声"嘎"就是开机第一声。

"声数=事件类别，闭眼数数"——清一色嘎会误以为重新录了一遍，其实是来消息（2026-09-25 用户定稿）。

## 硬件按键：零接触（ADR-059，2026-09-27 定稿）

**OPPO Watch X3 两颗物理键实测 `KEYCODE_F1`（右上）/ `KEYCODE_F2`（右下）**（2026-09-26 调试页实录）。历史结论留档：

- v0.2.2~0.2.8 期间 App 白名单拦截过它们（F2=切换录音、F1=返回），但冲突不断：**绑定"双击 F2 打开嘎嘎"后，F1 的"回主页"在 ColorOS 策略层执行，`onKeyDown` 返回 true 拦不住**——事件到了 App、系统照样回主页；白名单还把音量/相机/F3~F12/BUTTON_* 一并纳了进去，用户按任何键都可能触发录音。
- **"已拦截 ≠ 系统不动"**——策略层并行执行是 ROM 行为，App 层无解。

**现行策略**：App **不消费、不拦截、不映射任何物理键**（含媒体键，MediaSession 已删）。系统键回归系统语义；录音交互靠晃动/触屏/系统手势唤起。调试页按键记录保留（纯观察，进调试页按一下能看到 `keyCode` 和 `→ 交回系统`）。

实测新键值想看映射时：`adb shell getevent -l` 按一下看 `EV_KEY` 的 KEYCODE，或直接进调试页按。

**实测方法**：

```bash
adb shell getevent -l     # 按一下按钮，看 EV_KEY 的 KEYCODE
```

拿不到时的兜底（按代价从低到高）：`MediaSession`（已实现，对媒体类键有效）→ 无障碍服务 `AccessibilityService`（几乎全拦截，需用户授权）→ 做表盘 Watch Face（控制力最强，工程量最大）。

**v0.2.2 已修的真机 bug**（ADR-052 修订①/②）：端口回显、233dp 圆屏布局溢出、MQTT 状态可读、F1/F2 默认行为拦截。

**v0.2.5 已修（本轮优化）**：① **下行帧头解析致命 bug**——服务端下发的载荷带 3 字节帧头，v0.2.x 直接当 JSON 解析永远失败 = receipt/reply/error 从未到达过界面（手表只能发不能收，且零报错）；新增 `Frame.decode/decodeAll` 剥头（含多帧防御）。② **录音结尾丢字**——MediaCodec 停录时内部可能压着最后一包没吐，语句末尾 ~20-60ms 无声；停录前发 EOS 冲刷。③ **断链帧缓冲**（手表版 ADR-049）——MQTT 断开期间的帧按序存 RAM（上限 ≈2 分钟），重连订阅就绪后自动补发，中途再断回填头部保时序；"本期不做"里的离线录音缓存就此落地。

**v0.2.6 已修（2026-09-27，ADR-057）**：① **下行分片重组**——v0.2.5 只剥帧头不重组，而服务端下行按 512B/包分片（首包 `type|0x80`、len=整帧总长；中间包 `0x00`；尾包裸 type），**reply 中文几百字（UTF-8 3B/字）几乎必然超 509B**，分片首包 len=总长 > 单包实际字节 → `decodeAll` 凑不齐直接 break = 整条信令静默丢弃，"只能发不能收"。`Frame.Reassembler` 补齐重组（语义对齐 server `FrameReassembler` / esp32 `FrameAssembler`：凑齐交付、5s 超时、溢出/孤儿续帧自保）。② **调试页传感器恒 0**——传感器只有"晃动录音"开关开着才 start，默认关 = ACC/GYR 从没跑过，看着像手表没有这俩传感器；现在进调试页无条件 start，离开时按开关决定停不停。③ **双晃交互**——晃两下手腕 = 切换录音（两晃间隔 350ms~1400ms 算一次指令，防走路/抬手误触），**默认开**；调试页实时显示"待第1下 / 等第2下 x.xs"。④ 设置页版本号改动态读取（原硬编码 0.2.1 早已陈旧）。

**v0.2.7 消息历史持久化（2026-09-27）**：手表是随身设备，每次打开清空历史不可接受——① `MsgLog` 加持久化钩子（`Persist` 接口），每次变更全量落盘、启动时恢复；② 存储选 **SharedPreferences + JSON 数组**（`MsgStore`）：几十条 × 几百字节 = KB 级、无查询需求、唯一消费方是本进程，XML 文件落在手表闪存零依赖零 schema 管理（SQLite/Room 对这个量级是杀鸡用牛刀）；数据坏了整体丢弃重建，不做字段级迁移——消息历史不是资产；③ 设置页新增**消息保留 [ 20/50/100/200 条 ]**（默认 50，缩小立即截断旧卡）；④ 恢复时上次没等到结果的 pending 卡收尾成"超时"态——重启后 state=IDLE 不会再发 `rec_status_query` 对账，挂着只会永远"正在回复"。

**v0.2.8 紧握手势 = 切换录音（2026-09-27，ADR-058）**：借系统"紧握松开"手势识别（用户绑定到"打开嘎嘎"），App 前台时手势触发的启动意图走 singleTask 的 `onNewIntent` → `toggleRecord()`。紧握 #1 冷启动开录 → 紧握 #2 停止发送 → 紧握 #3 再开录，零按键零触屏零传感器常开。为什么不用六轴自识别：握拳信号比甩腕小一个量级、个体差异大、要 IMU 常开耗电；系统的识别免费且可靠。**待真机验证**：ColorOS 手势在 App 前台时是否触发（部分 ROM 只在息屏态生效）——不触发则退回"调试页采 ACC/GYR 波形样本再自研特征"的备选路线。

**v0.2.9 物理键零接触（2026-09-27，ADR-059）**：用户报"在软件里随便按上下键都会触发/结束录音，很奇怪"——删除 KEY_RECORD_KEYS/KEY_BACK_KEYS 白名单与 onKeyDown/onKeyUp 拦截，MediaSession 媒体键兜底一并删除。物理键全部交回系统，App 一个按键事件都不消费（调试页记录保留，纯观察）。

**v0.3.0 手势判据 v2 + 常亮 + 灭屏收尾（2026-09-27，ADR-060）**：真机实测推翻两个假设——① 紧握手势**只在表盘态有效**（App 前台系统不触发），onNewIntent 路径只对"系统唤起已在前台的 App"有效（如双击右下键），保留；② 晃动撞自动灭屏。本轮：① **判据 v2 = 单轴反向交替双脉冲**（同轴、反向、1.4s 窗内配对）——上下甩两下/左右摆两下都命中，走路/骑车颠簸（同向冲击）天然免疫；② **常亮加固**（布局 keepScreenOn + Window 级 FLAG 双保险）——灭屏掐手势传感器和后台网，录音交互整个失效；③ **灭屏/切后台自动收尾**——onPause 时若在录音就 stopAndSend，话已说到一半，直接发出去别烂在缓冲里。
