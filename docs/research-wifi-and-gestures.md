# 调研：WiFi 家模式 + 手势识别优化路线（2026-09-26）

状态：调研文档（用户提问的三个方向的可行性结论）。

## ① WiFi 模式下摇动录音能用吗？

**能用，且零改动。** 关键事实：

- 摇动检测（Wake.cpp）只依赖 IMU 与 AppState，与链路层零耦合
  （Link 抽象之下 GattServer/WifiTransport 互换，wake.tick 不感知）。
- 录音上行（UplinkPump）调 `ctx_->link->sendFrame`——同样链路无关。
- 唯一的前置条件：家模式要真正能跑起来。当前阻塞 = 内存
  （lwIP+MQTT BSS ~25KB 与 BLE 栈无法共存于 320KB 内部 RAM；ADR-039
  的二选一互斥方案代码已备，WifiTransport 未挂回构建）。
- **恢复路径**：main.cpp 取消 `if (false)` 家模式分支 + CMakeLists 挂回
  WifiTransport.cpp + 二选一互斥（家模式不启 NimBLE）。摇动/抬手/转向/
  离线缓存全部自动跟随，无需任何手势侧改动。

结论：**不是功能问题，是内存工程问题。** C3 协处理器（硬件路线）或
PSRAM 化 lwIP（深入调优路线）二选一后开启。

## ② 识别方案还能怎么优化？

当前 v4.1（dev>1.0 + 单摆峰值 2.5g + 4 摆 + 停手确认）在 12 场景数据集上：
摇 3~23 次触发，静息/敲/摔/走/掏全 0 误触，跑步 1 次/30s。已接近纯
加速度的物理上限。下一步的三个杠杆（按性价比排序）：

1. **陀螺仪节律门控**（数据已采，差算法）：跑步的角速度节律（脚步
   ~3Hz 全身起伏）与手摇（手腕周期 ~2Hz 高峰值）在 ⑥⑦ 段六轴数据里
   可分。给摆检测加"伴随 |gyro| 峰值 >80dps"条件，跑步误触可归零。
   代价：息屏也要开陀螺（+1~3mA）——可以只在高置信加速度段瞬时开启。
2. **跳变前的预筛**：跳一下/落地的特征是 |a| 尖峰**单侧**（落地大、
   起跳小）且间隔 >600ms；手摇双侧对称。已隐含在"4 摆 1s 窗"里，
   可再加"相邻摆幅度比 0.5~2.0"收紧。
3. ** personalised 阈值**：每人摇法力度不同，首次使用时引导摇 3 次
   自学习峰值基线（存 NVS）。体验最好，工程量最大，放最后。

## ③ 自动转向正确识别（v6 已进固件，待真机标定）

v5.1（ax 符号）对"挂脖→拿起"的相位仍有歧义。v6 改用**翻转方向定向**
（用户洞察）：

- 拿起瞬间陀螺仪 X 轴积分：从脖子翻上来的方向不同，积分符号相反；
  静止确认后 |积分|>60° 用符号定向，<60° 兜底 ax 符号。
- **待真机标定**：符号→0/180 的映射（一次实验：正着拿起来看
  `[ROT] 翻转积分 +XXX°` 还是负号，一行代码定死）。
- 定标台（scripts/calibration/orient_calib.py）已支持六轴实时显示，
  明天验证时直接看 gx 列。

## 附：APK/链路已落地的配套优化（2026-09-26）

- 下行合批（12ms/MTU 冲刷）：根治"文字秒到、音频等半分钟"的手机侧
  写入瓶颈（一次 BLE 写携多帧，设备 FrameDecoder 流式支持）。
- BLE 连接参数 30ms（省 4 倍 radio 唤醒）；广播间隔 105~305ms。
- 重连自动化：App 回前台重建扫描会话（ColorOS 后台限流的根治），
  伴生设备出现即踢重连 + 自动跟随设备换 MAC。
- 伴生设备 API 补满：手表 profile（系统级保活豁免）+ 三个
  REQUEST_COMPANION_* 权限。
- IMU 息屏降档：accel 500→94Hz + 陀螺关（传感器电流约减半）。
